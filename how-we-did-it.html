How we did it

This page is the method behind the RBNT holder report, written so that anyone can rerun it, check a number, or produce the next quarter. Edition 1 covers Q3 2026: 1 July to 30 September 2026.

In one paragraph

We read the Redbelly chain from its first block to the last block of 30 September, listed every address that could possibly hold RBNT, and asked the node what each one held at fixed blocks. Wrapped and staked RBNT is credited to the address that owns it. Unnamed addresses are only ever reported inside groups of five or more. Before any table is written, a set of exact checks has to hold to the wei; after the tables are written, a separate stage reads the published figures back from the node.

Dates and blocks

A date in this report means the end of that day in UTC, and it is stood for by the newest block whose timestamp is earlier than midnight. We find that block by bisecting on block timestamps from the node, confirm that the next block is stamped at or after midnight, and compare our answer with the explorer's getblocknobytime. (The explorer counts a block stamped exactly at midnight as "before"; we do not. That is the only difference we allow.)

The same rule gives a block for every day of the quarter (93 in all) and for every seventh day. Those are used for the pools, WRBNT and the reserved wallets.

How a holding is counted

An address's holding is its RBNT, plus its WRBNT balance, plus whatever it has staked in either pool (userInfo(address).amount). Because of this, wrapping or staking never looks like selling.

To count every coin exactly once:

  • RBNT held by the WRBNT contract backs WRBNT one to one, so it is credited to the WRBNT holders and not to the contract. If the contract ever held more RBNT than the WRBNT supply, the excess would be shown on its own; in this edition there was none.
  • RBNT staked in a pool is credited to the staker. What is left in the pool above its totalStake is the pool's reward reserve, shown separately.

Holder counts, size bands and concentration cover unnamed wallets holding at least 1 RBNT. Named wallets and contracts are shown elsewhere, because the reserved wallets are large by design and a single contract can hold coins for many people. A wallet is an address without code at the closing block (an address carrying only an EIP-7702 delegation marker still counts as a wallet); anything with code is a contract.

How we found every address

  1. Every block. For each block from 0 to 3,209,414 we read the receipts (eth_getBlockReceipts) and the header. Receipts give us every sender, receiver and newly deployed contract, plus every event emitted by WRBNT or either pool. Headers give us the 20-byte values listed in extraData, which is where Redbelly names its governors.
  2. Every internal transfer. Contracts also hand RBNT on while a transaction runs. The node we use cannot replay those calls, so we take them from the explorer's txlistinternal, by block range, starting at block 0. Whenever a range comes back at the 10,000 row limit we split it, so nothing is cut off.
  3. Public tags. We read the explorer's address list, largest first, and the WRBNT holder list, only to pick up public names and make sure no WRBNT holder is missed.

This gave 761,594 addresses. Governors matter because Redbelly pays fees to them as plain balance changes with no transaction attached, which is also why we never rebuild balances by adding up transfers.

How we read balances

  • RBNT of every address at the opening and closing blocks (eth_getBalance).
  • RBNT at both month ends for every address that was non-empty at either end or took part in any transfer during the quarter. Any other address held nothing at either end and never moved, so it held nothing in between.
  • WRBNT balanceOf at all four dates for every address that ever appeared in a WRBNT event or the explorer's holder list, and the WRBNT totalSupply.
  • userInfo in both pools at all four dates for every address that ever appeared in a pool event; each pool's totalStake and balance at every daily block.
  • getStakeUnlockTimes at the closing block for every open stake.
  • eth_getCode at the closing block for every address that held anything.

Balances in the explorer's lists are never used: they are today's figures and rounded.

How we sort contracts

For every contract that held at least 1 RBNT at one of the four dates we read the contract name from its verified source on the explorer (for a proxy, the name of the contract behind it). That name says what the program is, never who runs it. Names are matched in this order:

Name contains Kind
vest Token vesting contracts
safe, multisig, gnosis Shared-key wallets (Safe)
bridge, oft, portal, gateway, teleport Cross-chain bridge contracts
pair, pool, swap, router, amm, algebra, liquidity Exchange liquidity pools
stak, farm, reward Other staking programs
no verified source Contracts with no published code
anything else Remaining contracts

A kind with fewer than five contracts is shown as part of Remaining contracts.

Staking: stakes and reward reserve

Both pools run the verified contract ReddexRBNTLockStaker. A stake adds the RBNT sent to the staker's userInfo.amount and to the pool's totalStake; a withdrawal takes it off both and sends it back; rewards are paid in RBNT from the pool's own balance. A pool's RBNT balance is therefore the stakes plus a reserve for rewards. As the brief asks, the headline figure is the pool's RBNT balance at each date; next to it we show totalStake and the difference.

Stakes and withdrawals in the quarter are counted from the pools' own Stake and Unstake events, reward claims from ClaimLiquidXReward. A transfer into a pool that is not a call to stake() is a top-up of the reward reserve.

Named wallet flows

For each named wallet we take every successful transaction and every internal transfer with value between the two closing blocks, and group the other side by who they are: another named wallet by name, a contract by its kind, or otherwise "unnamed wallets". Fees are what the wallet paid for the transactions it sent. WRBNT moves of the reserved wallets are read from WRBNT Transfer, Deposit and Withdrawal events and listed separately, since moving a token does not change an RBNT balance.

Privacy safeguards

  • Only the addresses in the tables above are ever shown.
  • An unnamed address can contribute to a count or a total, but only inside a group that has five or more members. Size bands, stake sizes, contract kinds and unlock months are merged, or shown as "<5", wherever a group would be smaller.
  • Contract kinds come from the program's own published name. We never guess who is behind an address and never add a label the explorer does not show.
  • The per-address cache lives in cache/ and is never committed. The audit stage and the unit tests both fail if any other address appears in a published file.

The exact checks

These must all hold, in wei, before any table is written (58 checks in this edition, listed with their results in headline.json):

  • At each of the four dates, the WRBNT supply equals the sum of every WRBNT balance, and the WRBNT contract holds at least that much RBNT.
  • At each date, each pool's stakers add up to its totalStake, and the pool's balance covers its totalStake.
  • Over the quarter, for each pool, RBNT in Stake events minus RBNT in Unstake events equals the change in totalStake.
  • The unlock schedule of the 365 day pool adds up to its closing totalStake.
  • At each date, holdings (WRBNT and stakes credited to owners, reserves left in the pools) add up to the RBNT found.
  • The changes of all groups net to the change in RBNT found.
  • Every reported contract kind has at least five members.
  • Every named wallet balances: opening RBNT + RBNT in - RBNT out - fees = closing RBNT, with a gap of zero wei.
  • The balances found cover more than 99.99% of the supply and never exceed it.

The second read

After the tables are written, the audit stage reads, straight from the node and without the cache: every named wallet's balance at both dates, both pools' totalStake at both dates and the WRBNT supply at both dates. It also reads 600 cached balances again, picked at random with a fixed seed, re-tests every date's block, scans every published file against the house rules (no unnamed address, no long dashes, no emoji, no price talk, no credit lines) and checks every thread post fits in 280 characters. Results are in audit.json.

Coverage

All 10 billion RBNT existed from the first block. The balances we found add up to 99.99964% of the supply at the closing block. The remaining 36,485 RBNT sit at addresses that never appear in any transaction, internal transfer, event or header we read, such as addresses funded at launch and never touched. That remainder moved by about 11 RBNT during the quarter.

Running it, and the next edition

Python 3.11 or newer, the packages in requirements.txt, and a Chromium that Playwright can drive (set CHROMIUM_PATH to use a system Chromium).

pip install -r requirements.txt
make data      # blocks, crawl, traces, tags, holdings, programs (resumable)
make report    # tables, draw, publish, audit
make check     # offline: unit tests and the house-rules scan

Any single stage runs with PYTHONPATH=src python -m rbnt <stage>.

For Q4 2026:

  1. Copy config/q3-2026.json to config/q4-2026.json. Change edition, period and main_snapshots (month ends are named month_YYYY-MM-01), and set snapshot_blocks back to null.
  2. Look at the DAO treasury page again and update reserved_wallets if it has changed, with the date you read it.
  3. Run make data report EDITION=q4-2026. From an empty cache this reads about 3.4 million blocks; stretches with very busy blocks are split automatically.
  4. Read the new report from start to finish. Sentences that describe a direction are generated from the numbers, but read them against the charts.
  5. Publish only when the audit ends with no failures.

Known gaps

  • A block explorer can show that coins left an address; it cannot show who pressed the button or for what reason. A falling group total may be selling, a move between one owner's addresses, or a deposit into a contract.
  • Addresses are not people. One person can use many addresses and one exchange address can hold coins for many people.
  • Coins passed along inside contract calls are taken from the explorer's records rather than replayed on the node. The named wallets, the WRBNT contract and both pools pay out mostly that way, and all of them balance to the wei, which is our test that those records are complete.
  • Public tags were read for the 20,000 largest addresses in the explorer's list, so a tag on a smaller address would be missed.
